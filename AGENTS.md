# Working on LastPeek

Read `docs/product.md` and `docs/architecture.md` before changing behaviour. Keep the product focused on draft review; no external service may become mandatory.

Read `docs/design.md` before UI or copy changes. LastPeek supports Auto, Dark and Light appearances, is minimal and X-native in the composer and preview, with its own restrained coral identity. Use the semantic theme tokens in `src/app.css` rather than fixed interface colours. Reuse the shadcn-svelte components in `src/lib/components/ui`; use Phosphor icons. Fix confusing interactions instead of adding explanatory disclaimers. Mobile must retain desktop capabilities.

- Before adding or changing any interactive control, inspect `src/lib/components/ui` and reuse the prepared shadcn component. In particular, use the shared `Select` for dropdown fields, never a native `<select>` or a hand-built replacement. Do not assume a component is missing without checking. Use shared Dialogs for focused comparisons/viewers rather than native disclosure accordions in the review experience.
- NO generic success/information notices or prompts. Prefer the visible resulting state or feedback attached to the control that performed the action; never add a banner/toast just to repeat what is already obvious. Keep actionable errors local to their controls, and use dialogs only for real decisions or necessary confirmations. Use the shared shadcn Checkbox for every checkbox; do not introduce native or page-specific checkbox styling.
- TypeScript + SvelteKit, one server, PostgreSQL and private filesystem media. Server-only code belongs in `src/lib/server`. Contracts shared with UI belong in `src/lib`.
- `npm ci`, `npm run db:migrate`, `npm run db:seed`, `npm run dev` start development after PostgreSQL and `.env` exist. See README for Docker and orb setup.
- Iterate cheaply: run relevant static/unit checks and verify the changed behavior, not the whole release gate for every feature. Use `npm run verify:focused -- --test 'core / create and edit'` for a core browser workflow, `--browser webkit` for an engine-specific issue, or `--browser none --file tests/drafts-http.test.ts` for server/HTTP tests once. Temporary browser files directly under `tests/` can use the same `--file` option; remove them after verification. The command owns disposable fixtures; never borrow another verifier's database/server or inspect its process environment. Do not overlap verifier invocations within an orb.
- CI is the authoritative full gate: types, unit tests, build, migrations twice, server integration/HTTP contracts once, and the small Chromium/WebKit workflow suite. A feature agent is not required to duplicate it locally. Run `npm run verify:release` locally for harness/cross-cutting changes, diagnosing integration failures, or when CI is unavailable. Fetch before integration; verify the integrated tree, not just earlier feature trees. Local receipts reuse only unchanged tested inputs; `-- --force` runs everything, as CI always does. Do not edit source/tests during a full gate or treat a focused pass as a release certificate.
- Use a separate preview for screenshots/recordings, not a verifier's server. Establish health and hydrated UI readiness; preserve a browser session throughout a recording. Never overlap root `npm ci` with a running preview/build; verification uses private cached dependencies. Never run tests against a real user's instance.
- GitHub Actions verifies pull requests and publishes tested multi-architecture images on main. Never run untrusted pull requests on the Pi or grant them publishing credentials.
- When Alexander asks to ship, follow delivery all the way through deployment, not just the push. Read `docs/deployment.md`, watch the exact commit's CI and image-publishing jobs, then wait for the Pi's automatic update. Verify that `https://lastpeek.alexheffernan.dev/health` returns HTTP 200 with that commit's full SHA in `X-LastPeek-Revision`, and check the public page. For visual changes, inspect the deployed desktop and mobile layouts. Report completion only after those checks pass; otherwise keep investigating and report the specific blocker. Do not silently stop after saying CI is running or require a separate request to babysit deployment. Monitoring does not authorize manually accelerating deployment, changing production infrastructure or data, or rolling back; obtain separate approval when needed.
- Documentation-only releases intentionally skip image publishing; verify their lightweight workflow and existing production health instead of waiting for a documentation SHA to deploy. If an application release is superseded by newer application work, report that explicitly rather than claiming its skipped promotion deployed.
- Browser-verify visual changes at desktop and mobile widths, including failures and older-revision feedback. Use accessible labels, not implementation selectors, in tests.
- Preserve owner checks and capability checks in every server operation. Media must never move into `static`. Never log draft text, passwords or review tokens.
- Revisions are immutable. Autosave must use the expected edit version. Comments retain their original revision and post identity.
- Use SQL migrations; do not mutate schema automatically on requests. New abstractions need a real second consumer or a coherent responsibility.
- Do not commit `.env`, media, database volumes or test artifacts. No agent co-author trailers. Commit as the checkout's configured human identity.

## Test cost and coverage

- **Permanent Playwright budget: five workflows and one privacy exception in `tests/web.test.ts`.** Invited signup; sign in/out; create/edit with persistence; create/open a review link anonymously; reviewer feedback reaching the author. The exception checks service-worker private-data caching/offline behavior, which HTTP cannot establish. Run desktop Chromium and mobile-sized WebKit; this is browser emulation, not a real iPhone. Do not add feature-specific journeys, branches, pixel/copy assertions or a third browser to this gate by default. New permanent browser exceptions require Alexander's explicit approval and must explain why a lower-layer test is insufficient. Replace or simplify an obsolete workflow rather than preserving intentionally removed behavior.
- **Task verification is not permanent regression coverage.** For a UI change, exercise the changed interactions and representative desktop/mobile, success/failure and appearance states with a temporary Playwright script/test or agent-browser. Inspect captures and record interactions where useful. Report what was exercised and remove temporary scripts/fixtures; keep only useful review evidence, never credentials or private content. Do not turn every requested feature or repaired UI bug into a committed browser test. No nightly/quarantined copy of the deleted feature suite.
- Keep strong, permanent backend contracts for ownership/capabilities, CSRF, immutable revisions, optimistic concurrency, private media/revocation, authentication/session invalidation, billing and provider retry/idempotency. Use the cheapest sufficient layer: pure rules in `npm test`, database/provider behavior in `test:integration`, real HTTP/image behavior in `test:http`. Do not duplicate server assertions in both engines. Add/extend a test only for an observable, durable contract with a plausible regression that types/existing coverage miss; name the risk and choose distinguishing inputs. Intentional product changes should change or remove obsolete expectations, not preserve them with compatibility code.
- Each permanent workflow has fresh fixtures and is independently selectable. Seed prerequisites directly unless creating them is what it tests; clean pools, contexts and files on failure too. HTTP files run sequentially because global admin snapshots otherwise race other files' account teardown; concurrency contracts still issue parallel requests inside their test. Aim for individual browser workflows around 10 seconds or less and focused iteration around one minute; report measured runtimes for harness/browser changes. Profile a slow case with `DEBUG=pw:api npm run verify:focused -- --browser webkit --test 'name'` before changing its waits. Do not weaken a security assertion to meet a timing target.
- Wait for the real response or visible hydrated state, not arbitrary sleeps or blanket `networkidle`; an SSR button alone is not proof of working handlers. Assert persisted results, not only a click or mock request. Use controlled clocks for retry/expiry boundaries; short real autosave delays are acceptable in the tiny core suite. Keep gestures/video on real browser time. Never force clicks, add retries or raise timeouts to hide failures. Browser failure screenshots and error summaries survive disposable cleanup under `.amp/in/verification-failures/` and CI retains them for seven days.

## Integration and CI discipline

- Parallel orbs may implement independent features, but use one designated integration owner at a time for a batch. If none is designated, the agent handling the current ship request owns integration; coordinate active branches before landing overlapping work. Do not run a rebase/push race or independently ship the same batch from several orbs. This is a coordination convention, not a distributed lock.
- Feature agents deliver scoped changes plus targeted verification evidence. The integration owner incorporates them sequentially, runs relevant conflict checks, and lets CI certify the final integrated tree. A changed tree needs a new gate; a metadata-only rebase does not require identical local work when a receipt still matches. Do not batch unrelated fixes opportunistically.
- Bound the loop: inspect the first CI failure, reproduce the exact failing selection locally, and allow one evidence-based repair/push. If it fails again, stop the ship loop and diagnose the named failure with scoped checks and retained evidence; report the blocker before another push. Do not repeatedly rerun the full gate, blindly retry CI, rewrite expectations just to get green, or waive a required check. Separate a product defect, an obsolete expectation and a fixture/hydration failure before choosing a fix. Shipping still follows the deployment rules above.

## Production site administration

- For production accounts, draft/storage totals, API usage, feature flags or access history, use the project Amp plugin `.amp/plugins/lastpeek-ops.ts` first. Discover `admin_overview`, `admin_users`, `admin_usage`, `admin_flags` and `admin_history` with `tool_search`, then call them through `code_exec`. Search accounts with `admin_users` to obtain a `userId` for per-account reads.
- Read `docs/operations.md` for tool parameters, access limits and troubleshooting. New LastPeek orbs load the plugin and configured restricted access; existing threads may need to reload the plugin. Report missing tools, credentials or connectivity rather than bypassing the gateway or asking for secrets in chat.
- Admin reads are read-only. Feature changes use `set_feature_access`; accounting decisions use `reconcile_usage` and `reconcile_x_balance`, only with the user's authorization and the plugin's human confirmation. Accounting writes select exact unresolved IDs or a fresh payer snapshot and preserve original provider evidence. They require the updated host gateway and existing write credential; never bypass missing gateway access. The gateway cannot change admin membership, perform bulk feature grants or deploy.
- The orb's PostgreSQL database is disposable development data, **not production**. Never use it to answer production questions or run E2E tests against production. Registered-account totals are not live-online or recent-activity counts; report only what the tools actually measure.
