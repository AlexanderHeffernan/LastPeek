# Working on LastPeek

Read `docs/product.md` and `docs/architecture.md` before changing behaviour. Keep the product focused on draft review; no external service may become mandatory.

Read `docs/design.md` before UI or copy changes. LastPeek is dark-only, minimal, X-native in the composer and preview, with its own restrained signal-green identity. Reuse the shadcn-svelte components in `src/lib/components/ui`; use Phosphor icons. Fix confusing interactions instead of adding explanatory disclaimers. Mobile must retain desktop capabilities.

- NO generic success/information notices or prompts. Prefer the visible resulting state or feedback attached to the control that performed the action; never add a banner/toast just to repeat what is already obvious. Keep actionable errors local to their controls, and use dialogs only for real decisions or necessary confirmations. Use the shared shadcn Checkbox for every checkbox; do not introduce native or page-specific checkbox styling.
- TypeScript + SvelteKit, one server, PostgreSQL and private filesystem media. Server-only code belongs in `src/lib/server`. Contracts shared with UI belong in `src/lib`.
- `npm ci`, `npm run db:migrate`, `npm run db:seed`, `npm run dev` start development after PostgreSQL and `.env` exist. See README for Docker and orb setup.
- Iterate cheaply: run static/unit checks, then `npm run verify:focused -- --test 'test name regex'` (both engines by default); for example, `--test 'author / composer and media'` runs only that scenario. Add `--browser webkit` to reproduce a browser-specific failure or `--file tests/x-publishing.test.ts` to select another file. This command owns its disposable fixtures; never borrow another verifier's database/server or inspect its process environment. Focused passes do not certify a release. Prefer independently selectable tests over extending unrelated long journeys. Do not launch overlapping verifier invocations: the harness already owns bounded engine/scenario parallelism, and oversubscribing WebKit makes it slower and unreliable.
- Finish focused checks and desktop/mobile visual inspection before starting the final release gate. If it fails, reproduce the failing test with `verify:focused`, fix it, then rerun the gate; do not repeatedly run the entire gate to diagnose one timeout. Do not edit source/tests during final verification. Use a separate preview for screenshots/recordings, wait for its health and required UI state, and preserve one browser session throughout each recording. Never overlap root `npm ci` with a running preview/build; verification uses private cached dependencies instead.
- Run `npm run verify:release` for behavioural changes; it includes types, unit tests, production build, migration idempotence and Chromium/WebKit E2E in isolated disposable databases/media/builds. Fetch before verification and rerun the command after integrating changes: its local receipt reuses checks only when tested runtime/test/tooling inputs are unchanged, while formatting and audit always rerun. Use `-- --force` for a fresh full run; CI always does so. Do not rebuild/restart its test server for screenshots or recordings. Never point E2E at a real user's instance.
- GitHub Actions verifies pull requests and publishes tested multi-architecture images on main. Never run untrusted pull requests on the Pi or grant them publishing credentials.
- When Alexander asks to ship, follow delivery all the way through deployment, not just the push. Read `docs/deployment.md`, watch the exact commit's CI and image-publishing jobs, then wait for the Pi's automatic update. Verify that `https://lastpeek.alexheffernan.dev/health` returns HTTP 200 with that commit's full SHA in `X-LastPeek-Revision`, and check the public page. For visual changes, inspect the deployed desktop and mobile layouts. Report completion only after those checks pass; otherwise keep investigating and report the specific blocker. Do not silently stop after saying CI is running or require a separate request to babysit deployment. Monitoring does not authorize manually accelerating deployment, changing production infrastructure or data, or rolling back; obtain separate approval when needed.
- Documentation-only releases intentionally skip image publishing; verify their lightweight workflow and existing production health instead of waiting for a documentation SHA to deploy. If an application release is superseded by newer application work, report that explicitly rather than claiming its skipped promotion deployed.
- Browser-verify visual changes at desktop and mobile widths, including failures and older-revision feedback. Use accessible labels, not implementation selectors, in tests.
- Preserve owner checks and capability checks in every server operation. Media must never move into `static`. Never log draft text, passwords or review tokens.
- Revisions are immutable. Autosave must use the expected edit version. Comments retain their original revision and post identity.
- Use SQL migrations; do not mutate schema automatically on requests. New abstractions need a real second consumer or a coherent responsibility.
- Do not commit `.env`, media, database volumes or test artifacts. No agent co-author trailers. Commit as the checkout's configured human identity.

## Test cost and coverage

- Keep a permanent test only for an observable contract and a plausible regression that existing coverage/types would miss. Name that risk and use an input that distinguishes correct from incorrect behavior. Extend the relevant case before adding another; use temporary probes for one-off implementation checks, then remove them.
- Test at the lowest sufficient layer: pure rules in `npm test`, database/provider contracts in `test:integration`, running-server HTTP/image contracts in `test:http`, and actual DOM, navigation, hydration, gestures, media playback and service-worker behavior in `test:e2e`. Server-only work runs once, not once per browser. Keep Chromium and WebKit for browser-dependent behavior; do not remove security/ownership/concurrency coverage to meet a time target.
- Give unrelated scenarios independently selectable names and their own fixtures; do not append them to the large author/admin journeys. Seed prerequisites directly unless creating them through the UI is the behavior under test. Share a workflow only when its sequence is itself the contract. Aim for a complete focused iteration under one minute, with individual browser scenarios around 10 seconds or less; profile and split slow scenarios instead of raising timeouts. Register pool/context/file cleanup so focused selections and failures exit cleanly. When separating a journey, preserve its ownership, offline-storage and browser-error assertions in every relevant independent scenario, not just the last one.
- Wait for the response or visible state that proves readiness, not arbitrary sleeps or blanket `networkidle`. A visible SSR button alone does not prove its JavaScript handlers are hydrated; establish readiness before testing its first interaction. Use a controlled clock for server retry/expiry deadlines and assert both sides of the boundary. For browser tests that are not measuring elapsed time, advance autosave and transient-feedback timers rather than waiting through every debounce; still assert the actual HTTP result and resulting UI state. Keep scrolling, animation, video and hold-gesture tests on real browser time. A real browser timing contract (such as the 1.5-second hold) may need bounded elapsed time; explain it. Do not force clicks, bypass actionability, add retries, or increase timeouts to hide a failing scenario.
- Viewport changes and new pages are expensive in WebKit. Reuse a page within a coherent scenario, group checks at each relevant width, and avoid repeating identical layout assertions after every operation. Preserve mobile capabilities, failure states and genuinely different breakpoints.
- Report the affected test's measured runtime when adding browser/media coverage, and compare the full gate when changing the harness. Profile a slow test with `DEBUG=pw:api npm run verify:focused -- --browser webkit --test 'name'` before changing waits or coverage. No hard runtime budget justifies weakening assertions.

## Production site administration

- For production accounts, draft/storage totals, API usage, feature flags or access history, use the project Amp plugin `.amp/plugins/lastpeek-ops.ts` first. Discover `admin_overview`, `admin_users`, `admin_usage`, `admin_flags` and `admin_history` with `tool_search`, then call them through `code_exec`. Search accounts with `admin_users` to obtain a `userId` for per-account reads.
- Read `docs/operations.md` for tool parameters, access limits and troubleshooting. New LastPeek orbs load the plugin and configured restricted access; existing threads may need to reload the plugin. Report missing tools, credentials or connectivity rather than bypassing the gateway or asking for secrets in chat.
- These admin tools are read-only. Feature changes use `set_feature_access` only with the user's authorization and the plugin's human confirmation. The gateway cannot change admin membership, perform bulk writes or deploy.
- The orb's PostgreSQL database is disposable development data, **not production**. Never use it to answer production questions or run E2E tests against production. Registered-account totals are not live-online or recent-activity counts; report only what the tools actually measure.
